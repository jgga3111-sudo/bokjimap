# 복지온(가칭) — 지자체 복지·지원금 정보 사이트 기획

작성일: 2026-08-31
성격: 러닝온(runningon.co.kr)의 두 번째 사이트. 애드센스 수익화 목적.

---

## 1. 왜 이 주제인가

러닝온 코드베이스와 라이브 사이트맵(1,189 URL)에서 성공 요인을 역산한 결과,
러닝온이 이긴 이유는 시장이 커서가 아니었다. 러닝온 시장 크기는 네이버
데이터랩 앵커 환산 **4.3**으로 조사한 33개 주제 중 최하위권이다(계산기툴 72.9,
운세 461). 이긴 이유는 다음 세 가지였다.

1. **수집형 구조** — 1,189 URL 중 1,134개(95%)가 "세상에 이미 있는 개체 1개 = URL 1개".
   직접 쓴 글(가이드)은 40개, 3%뿐.
2. **파편화가 곧 진입장벽** — 마라톤 대회 353개가 조직위 홈페이지에 흩어져 있고
   통합 DB가 없었다. 모으는 것 자체가 해자였다.
3. **축 조합으로 URL 증폭** — 지역 17 × 시기 × 종목으로 115개 랜딩 자동 생성.
   단 `MIN_RACES = 3`으로 얇은 페이지는 차단.

복지·지원금은 이 세 조건을 모두 만족한다. 226개 시군구가 각자 공고를 내
파편화가 가장 심하고, 개체(복지서비스)가 명확하며, 지역축이 최강이다.
시장 크기는 앵커 환산 **50.9 = 러닝온의 11.8배**.

경쟁 상황: AI 양산 블로그가 틀린 정보를 도배하는 영역이다. 러닝온에서 이미
확립한 규율(확인 못 하면 null, 출처 대조, `verifiedAt` 기록)이 여기서 가장
희소한 자산이 된다.

## 3. URL 구조 (러닝온 패턴 이식)

### 러닝온 실측 구성
```
/courses/[id]          665개 (56%)   장소 개체
/races/[id]            354개 (30%)   이벤트 개체
/marathon/[...slug]    115개 (10%)   축 조합 랜딩
/guide/[slug]           40개 ( 3%)   직접 작성 글
------------------------------------------------
                     1,189개
```

### 복지온 대응 설계
```
/service/[id]               복지서비스 상세      중앙 367 + 지자체 N
/region/[sido]              시도 허브            17
/region/[sido]/[sigungu]    시군구 허브          226
/target/[slug]              대상별 허브          8~15
/welfare/[...slug]          지역 × 대상 조합     MIN_SERVICES=3 필터 적용
/guide/[slug]               신청방법 가이드      직접 작성
/calendar                   신청 마감 캘린더     러닝온 /calendar 이식
```

**대상(target) 축 후보**
청년 / 신혼부부·출산 / 노인 / 장애인 / 한부모 / 아동·보육 / 소상공인·자영업 /
저소득 / 구직·실업 / 농어민

**조합 페이지 상한**
226 시군구 × 10 대상 = 이론상 2,260. 실제로는 `MIN_SERVICES = 3` 필터를 통과한
조합만 생성한다. 러닝온이 `MIN_RACES = 3`으로 얇은 페이지 양산을 막은 것과 동일.
주석 원문: *"목록이 한두 줄뿐인 페이지를 수백 개 찍어내면 저품질 페이지 양산으로
오히려 손해다."*

| 항목 | 러닝온 | 복지온 | 격리 방식 |
|---|---|---|---|

| Git | `jgga3111-sudo/runningon` | 새 저장소 | 완전 분리 |
| Vercel | runningon 프로젝트 | 새 프로젝트 | 분리 |

| dev 포트 | 3000 | **3001** | 동시 실행 대비 |

| 애드센스 | 승인됨 | 계정에 사이트 추가 → 별도 검토 | 같은 계정, 다른 사이트 |

### Supabase를 초기에 쓰지 않는 이유
Supabase Free는 **활성 프로젝트 2개**까지이고, **1주일 무활동 시 자동 중지**된다.
러닝온이 이미 1개를 쓰고 있어 여유가 딱 1개뿐이고, 자동 중지가 걸리면 사이트가
죽는다. 복지 데이터는 갱신주기가 연 1회 수준이라 DB가 필요 없다. 러닝온도
`races.json`(552KB) 파일로 353개 대회를 관리하고 있다. 같은 방식으로
`services.json`을 쓰고, 커뮤니티 같은 동적 기능이 실제로 필요해질 때 도입한다.

### CLAUDE.md를 복사하면 안 되는 이유
러닝온 CLAUDE.md에는 배포 규칙(커밋 작성자 `fccls`로 고정, 아니면 Vercel Blocked),
인스타 계정, `PROMO_SECRET`, 쿠팡 스크립트 한도가 박혀 있다. 복사하면 두 사이트
설정이 섞여 사고가 난다. 새로 쓴다.

또한 러닝온 CLAUDE.md에는 *"이 저장소는 다른 세션도 동시에 작업 중일 수 있다.
`git add -A` 금지"* 경고가 있다. 저장소를 완전히 분리해야 이 위험이 안 넘어온다.

### 디스크
C: 여유 **862GB**. Next.js 프로젝트 하나당 `node_modules` 약 500MB.
D:는 여유 4GB뿐이라 쓰지 말 것.

## 7. 도메인

- 러닝온이 `.co.kr`이므로 통일. 국내 사이트 신뢰도에도 유리.
- 가격: `.co.kr` 연 13,500~22,000원 (가비아 최저, 닷홈·카페24 22,000원)
- **`.go.kr`은 정부기관 전용이라 취득 불가.** 시도하지 말 것.
- **"복지로"는 정부 공식 포털 이름이다.** 혼동되는 이름은 피한다.
  정부 사칭으로 읽히면 애드센스 심사에서도 불리하다.

### 확정: `bokjimap.co.kr` (복지맵)

2026-08-31 사용자 확정. 러닝온(`runningon.co.kr`)과 TLD를 통일했다.
DNS 확인 결과 **NS·A 레코드 모두 없음** → 미등록 가능성 높음(등록업체 검색창에서 최종 확인).

**등록처는 가비아를 권한다.** `runningon.co.kr`의 NS가 이미
`ns.gabia.co.kr / ns.gabia.net / ns1.gabia.co.kr`이므로 두 도메인의 DNS 관리가 한곳에 모인다.

사이트명: **복지맵**

### 후보 (DNS 1차 확인, 2026-08-31)

`.kr`이 `.co.kr`보다 3글자 짧아 말하기·타이핑 모두 쉽다. `.kr`을 우선한다.

| 도메인 | 의미 | DNS | 평가 |
|---|---|---|---|
| `bokjimap.kr` | 복지맵 | 응답없음 | **1순위.** 226 시군구 지역축과 의미가 정확히 일치 |
| `mybokji.kr` | 마이복지 | 응답없음 | **2순위.** "마이" 접두어가 익숙, 들으면 바로 타이핑됨 |
| `bokjimo.kr` | 복지모 | 응답없음 | 3순위. 짧지만 "모"의 뜻이 애매 |
| `allbokji.kr` | 올복지 | 응답없음 | 한 글자 김 |
| `dowoom.kr` | 도움 | 응답없음 | 발음은 쉬우나 `doum`/`dowoom` 표기가 갈림. 복지 키워드 없음 |
| `bokjizip.kr` | 복지집 | 응답없음 | `zip`이 압축파일로 읽힘 |

**이미 사용 중(제외)**: `bokjion.co.kr`(222.122.39.25) · `bokji.co.kr`(121.78.127.249) ·
`jiwon.kr` · `bokjinow.co.kr` · `bokjihub.co.kr` · `bokjida.co.kr` · `bokjinara.co.kr` ·
`bokjicheck.co.kr` · `jiwonkum.co.kr` · `jiwonzip.kr` · `doum.co.kr` · `doumi.kr`

**주의: "응답없음"은 구매 가능이 아니다.** 등록만 해두고 DNS를 안 붙인 도메인은
A 레코드가 없다. 짧은 이름일수록 이 경우가 흔하다. 최종 확인은 반드시 등록업체
검색창에서 한다.

`.kr`/`.co.kr`은 **국내 거주자만** 등록 가능(실명인증 필요).

구매는 본인이 직접 결제해야 한다(대행 불가).

## 8. 착수 순서

1. 공공데이터포털 회원가입 → 두 API 활용신청(자동승인) → 인증키 발급
2. **지자체복지서비스 실제 건수·필드 측정** ← 이게 나와야 URL 총량이 확정된다
3. 도메인 구매
4. Next.js 16 프로젝트 생성 (`welfare-hub`, 포트 3001)
5. 러닝온 모듈 이식 (sitemap / jsonld / collections / robots)
6. 데이터 수집 스크립트 + 정합성 검사
7. 콘텐츠 30~50페이지 쌓인 뒤 애드센스 사이트 추가 신청

**애드센스는 마지막이다.** 빈 사이트로 신청하면 "가치 없는 콘텐츠"로 거절되고
재신청 대기가 길어진다.
